## 摘要

山河纪是一个面向游客和管理员的全国热门景点文旅门户。游客可以浏览景点、按条件筛选、查看图集与介绍视频、阅读多日路线和游记、注册登录后预约门票、收藏内容并投稿游记。管理员可以维护景点、分类、票种、路线、订单、游记审核、评论、用户、轮播和资讯，并在数据统计页查看订单趋势、热门景点、用户增长和分类占比。

系统采用前后端分离。浏览器只负责页面和交互，业务规则放在 Spring Boot 接口中，数据放在 MySQL。图片和视频不写死在 Vue 组件里：封面、图集和视频地址分别存在 `scenic_spot.cover_url`、`spot_image.url` 和 `scenic_spot.video_url`。当前使用的照片来自 Wikimedia Commons 的自由授权作品，已压缩为 WebP，署名与协议见 `docs/ATTRIBUTION.md`。介绍视频只保存外链，不把视频文件放进仓库，因此在包含全部照片的情况下，源码压缩包仍可以控制在大约 10 MB。其中 9 个景点使用 Archive.org 直链，国内部分网络可能较慢；峨眉山、曲阜三孔、平遥古城目前没有介绍视频。

关键词：文旅门户；前后端分离；Vue 3；Spring Boot；MySQL；门票预约；自由授权图片

## 1 绪论

### 1.1 背景

各地景区已经普遍使用网上预约。一个课程规模的文旅网站不需要接入真实支付和闸机，但应该把游客真正会走的路径做完：先被首页吸引，再按省份或关键词找到景点，看开放时间和票价，选定日期下单，事后在订单里取消；有经验的游客还会写游记，管理员决定这篇游记能不能公开。山河纪按这条路径设计，而不是只做若干互不关联的静态页。

### 1.2 目标

1. 提供完整的游客前台和管理后台，页面之间可以互相跳转。
2. 用真实的著名景区组织内容，使列表、详情和统计看起来是在用的系统。
3. 数据库表结构清楚，主键、外键、索引和字段注释齐全。
4. 图片、视频和署名都由数据驱动，更换媒体时不改业务代码。
5. 给出可重复执行的建库脚本、部署说明和本设计报告。

### 1.3 范围与非目标

范围内包括注册登录、景点检索、详情、路线、游记、评论、收藏、门票预约、订单取消、内容审核和统计图。

范围内不包括真实支付、短信、身份证实名、景区官方库存同步，以及把视频文件下载进仓库。票价、库存和开放时间都是演示数据，页面上写明不能当作入园凭证。

## 2 需求分析

### 2.1 角色

系统有两类登录用户，外加未登录访客。

| 角色 | 能做的事 | 不能做的事 |
| --- | --- | --- |
| 访客 | 浏览首页、景点、路线、已通过的游记和资讯；查看评论 | 预约、收藏、发游记、发评论、进入后台 |
| 游客 USER | 访客的全部能力，加上预约、取消自己的待出行订单、收藏、投稿和编辑自己的游记、修改资料 | 审核他人游记、改票价、看全站订单 |
| 管理员 ADMIN | 游客能力之外，维护全部主数据，审核游记，隐藏评论，修改订单状态，查看统计 | 禁用自己，或停用最后一个正常状态的管理员 |

角色存在 `user.role`，取值 `USER` 或 `ADMIN`。接口用 JWT 里的 `role` 声明做判断，前端路由只负责把人带到该去的页面，真正的拒绝发生在服务端。

### 2.2 游客功能

1. 首页：轮播、主题分类、热门景点、推荐路线、最新资讯和已通过的游记。轮播点击后进入对应景点。
2. 景点列表：关键词同时匹配名称和城市，可按分类、省份、票价区间和排序（热度、最新、价格升降）筛选，每页 9 条。
3. 景点详情：大图与缩略图切换、作者和许可、介绍视频、开放时间、地址、复制地址、地图外链、票种价格、收藏、评论。
4. 推荐路线：多日行程，按天列出景点，可以从路线进入景点详情。路线参考价不含大门票。
5. 游记：只公开 `APPROVED`。作者可以投稿，正文至少 20 字。点赞对同一用户只计一次。编辑后回到待审核。
6. 门票预约：选择今天起 60 天内的日期、票种和 1 到 6 张票，填写联系人。提交后生成订单号。待出行订单可取消，取消后该日库存退回。
7. 个人中心：资料、密码、收藏、我的游记，以及通往订单列表的入口。
8. 注册与登录：用户名 4 到 20 位字母数字或下划线，密码至少 6 位。

### 2.3 管理功能

后台路径以 `/admin` 开头，接口以 `/api/admin` 开头。

| 模块 | 主要操作 |
| --- | --- |
| 数据统计 | 用户数、在售景点数、有效订单、成交额、今日订单、游记数量；四张图 |
| 景点 | 新增、编辑、上下架；同时维护封面、视频地址、视频署名和图集 |
| 分类 | 名称、印记、说明、排序 |
| 票种 | 按景点维护价格、日库存和在售状态；保存后回写景点起价 |
| 路线 | 天数、参考价、站点的天数和顺序 |
| 订单 | 按状态和关键字检索，直接修改状态 |
| 游记审核 | 查看正文，通过或驳回；驳回必须填写原因 |
| 评论 | 隐藏或删除 |
| 用户 | 修改角色和启用状态 |
| 轮播与资讯 | 上下线、排序、封面和正文 |

### 2.4 非功能需求

1. 界面为简体中文，桌面和手机都能完成主要路径。手机宽度下导航收进“菜单”。
2. 列表必须分页，单页最大 50 条，避免一次拉出全表。
3. 首页聚合接口缓存 120 秒。景点、游记、轮播或资讯变更时主动清掉这块缓存。
4. 密码只存 BCrypt 哈希。接口响应不返回密码字段。
5. 写操作放在事务里。预约要同时检查景点、票种、日期和当日已售数量。
6. 时间统一为 `Asia/Shanghai`，避免统计图的“今天”和导入脚本的 `CURDATE()` 相差一天。
7. 图片使用 WebP，列表封面用缩略图，画廊用较大的图，并给缩略图加 `loading="lazy"`。

### 2.5 用例叙述

以“林晓晚预约故宫”为例。她打开首页，从轮播或热门景点进入故宫。详情页能看到金水河一带的照片、作者 xiquinhosilva、协议 CC BY 2.0，以及一条指向原始文件页的链接。介绍视频使用故宫对应的 Wikimedia 地址。她选择成人票、日期和张数，填写手机号后提交。系统生成 `SH` 开头的订单号，状态为待出行。若她在订单页取消，该票种在这一天的已售数量会减少。

以“管理员审核游记”为例。陈一楠写的黄山草稿状态是 `PENDING`，公开列表里没有它，作者本人和管理员可以打开详情。管理员在“游记审核”里看到待审列表，点通过后状态变为 `APPROVED`，首页和游记列表在缓存过期或被清除后出现这篇游记。

## 3 总体设计

### 3.1 架构

浏览器里的 Vue 应用通过 axios 访问 `/api`。开发时 Vite 把 `/api` 代理到 `127.0.0.1:8088`。生产镜像里由 Nginx 把 `/api` 反代到后端容器，其余路径回退到 `index.html`，以支持前端路由。

后端按控制器、服务、映射器分层。控制器只做参数接收和调用服务。服务编写业务规则。映射器继承 MyBatis-Plus 的 `BaseMapper`，少数统计语句用手写 SQL。统一响应、参数校验和异常由公共组件处理。

```text
浏览器 Vue 3
    |  HTTP /api  JSON
Spring Boot 3
    控制器 -> 服务 -> 映射器
                |
             MySQL 8  库 shanhe
静态图片  frontend/public/media/images/*.webp
```

### 3.2 前后端分离与 MVC

这里的 MVC 体现在两端，而不是一个服务端模板引擎。

前端：Vue Router 是控制器的入口，Pinia 保存登录态，视图是 `views/` 下的单文件组件，接口模块 `src/api` 相当于模型的远程部分。页面不拼接 SQL，也不计算库存。

后端：控制器对应 C，实体和 VO 对应 M 的数据形态，服务里的规则是业务核心。页面 HTML 不由 Thymeleaf 输出。这样前后端可以独立启动，接口也可以用脚本直接验收。

### 3.4 技术选择

| 需求 | 选择 | 理由 |
| --- | --- | --- |
| 前台 | Vue 3、Vite、Vue Router、Pinia | 组件化页面和前端路由，官方脚手架 |
| 组件 | Element Plus | 表格、表单、分页、日期选择，并使用中文语言包 |
| 统计图 | ECharts | 只在统计页导入，避免拖进每个页面 |
| 请求 | axios | 拦截器统一附带令牌和错误提示 |
| 后台 | Spring Boot 3、Java 17 | REST、校验、事务 |
| 持久化 | MyBatis-Plus 3.5.8 | 分页和条件构造清晰；3.5.9 把分页拦截器移出了原包，故固定 3.5.8 |
| 认证 | JWT（jjwt 0.12.6）+ BCrypt | 不引入整套 Spring Security，仍能区分游客和管理员 |
| 缓存 | Caffeine | 首页 120 秒，进程内即可 |
| 数据库 | MySQL 8、utf8mb4 | 中文、外键和索引 |

没有使用 JPA。表名 `user`、`route` 与 SQL 关键字或 Java 类型容易冲突，MyBatis-Plus 可以用 `@TableName` 显式指定，比自动命名更可控。

### 3.5 页面地图

游客端布局 `UserLayout` 包含顶栏、搜索、页脚和回到顶部。登录和注册不套这层布局，避免截图和视觉上出现两层导航。

| 路径 | 页面 | 是否需要登录 |
| --- | --- | --- |
| `/` | 首页 | 否 |
| `/spots`、`/spots/:id` | 列表、详情 | 否 |
| `/book/:id` | 预约 | 是 |
| `/routes`、`/routes/:id` | 路线 | 否 |
| `/notes`、`/notes/:id` | 游记 | 否，仅已通过的对访客可见 |
| `/notes/new`、`/notes/:id/edit` | 投稿、编辑 | 是 |
| `/news`、`/news/:id` | 资讯 | 否 |
| `/orders`、`/user` | 订单、个人中心 | 是 |
| `/login`、`/register` | 登录、注册 | 否 |
| `/admin/**` | 管理后台 | 管理员 |

路由守卫读取 `meta.auth` 和 `meta.admin`。未登录访问预约会被送到 `/login?redirect=`，登录成功后回到原页面。非管理员访问 `/admin` 会回到首页。这只是体验层，接口仍会返回 401 或 403。

## 4 数据库设计

### 4.1 设计原则

1. 业务实体各自一表，多对多用关联表，不把景点名单塞进路线的一个文本字段。
2. 每张表都有主键。能确定归属的引用都建外键，删除策略按业务选择级联、置空或限制。
3. 评论和收藏指向景点、路线或游记中的一种，使用 `target_type + target_id`。这种多态不给 `target_id` 建外键，改由服务层检查目标是否存在。
4. 订单保存下单时的单价，不随后来的调价改变。
5. 游记点赞用 `note_like` 的唯一键保证一人一篇只能赞一次，`travel_note.like_count` 是冗余计数，方便列表排序。
6. 每个字段都有中文注释。字符集为 `utf8mb4`。

### 4.2 概念结构


`comment` 和 `favorite` 的多态关系没有画成外键。`banner` 和 `news` 是独立内容表。下图把 14 张表放在同一张图里，下面八段按业务把外键和多态读完。导出到 A4 时这张图按版心宽度排布，大约占四分之三页。

![十四张表的概念结构](diagrams/er.png)

用户表向外连出订单、游记、评论、收藏和点赞。景点表是另一端的中心：分类指向它，图集和票种从它分出去，订单、路线站点和游记再指回来。路线和景点是多对多，中间表 `route_spot` 记录第几天、第几站。订单同时指向用户、景点和票种，并保存下单时的单价。游记的景点可空，点赞用联合唯一键保证一人一篇只记一次。资讯和轮播不挂外键，首页聚合时再把它们和景点、路线拼在一起。

这张图不代替附录里的字段表。附录按列写出类型和注释，这里只回答“谁引用谁”。评论和收藏如果硬画成指向三张表的外键，数据库无法用一个 `target_id` 同时满足三套约束，所以服务层在写入前检查目标是否存在、是否对当前用户可见。

### 4.4 完整性与索引

外键包括：景点指向分类；图片、票种指向景点；订单指向用户、景点和票种；游记指向作者，关联景点可空且删除景点时置空；路线站点同时指向路线和景点；点赞同时指向游记和用户。

常用索引：

| 索引 | 用途 |
| --- | --- |
| `user.uk_user_username` | 登录和注册查重 |
| `scenic_spot.idx_spot_filter` | 上架状态 + 分类 + 省份 |
| `scenic_spot.idx_spot_visit`、`idx_spot_price` | 热度和价格排序 |
| `spot_image.idx_image_spot` | 画廊按景点排序 |
| `ticket_type.idx_ticket_spot` | 详情页只取在售票 |
| `booking_order.idx_order_ticket_date` | 计算某票种某日已售 |
| `booking_order.uk_order_no` | 订单号唯一 |
| `travel_note.idx_note_status_created` | 公开列表和待审列表 |
| `note_like.uk_note_like` | 防止重复点赞 |
| `favorite.uk_favorite` | 防止重复收藏 |
| `comment.idx_comment_target` | 按目标拉取可见评论 |

省份列表使用 `CONVERT(province USING gbk)` 排序，让中文省份按音序而不是 Unicode 码点排列。

### 4.5 状态约定

| 对象 | 取值 |
| --- | --- |
| 用户角色 | `USER`、`ADMIN` |
| 启用类状态 | `1` 正常或上架，`0` 禁用或下架 |
| 订单 | `PENDING` 待出行，`COMPLETED` 已完成，`CANCELLED` 已取消 |
| 游记 | `PENDING` 待审，`APPROVED` 通过，`REJECTED` 驳回 |
| 评论 | `VISIBLE` 展示，`HIDDEN` 隐藏 |

统计里的有效订单和成交额都排除已取消订单。

### 4.6 媒体字段

这是本项目和“把图片路径写在组件里”的主要差别。

| 字段 | 含义 | 当前内容 |
| --- | --- | --- |

## 5 接口设计

成功时 HTTP 状态为 200，响应体为：

```json
{ "code": 0, "message": "ok", "data": {} }
```

业务错误多数仍返回 HTTP 200，用 `code` 区分，例如 400。401 和 403 使用真实 HTTP 状态，axios 才能在未登录时跳转登录页。未知异常记日志并返回“服务器开小差了”，不把堆栈给浏览器。

### 5.2 管理接口

全部位于 `/api/admin`，需要管理员。包括分类、景点、票种、路线、轮播、资讯的增删改查，以及 `/stats`、`/orders`、`/notes` 与 `/notes/{id}/audit`、`/comments`、`/users/{id}`。

景点保存时用一份请求带上图集。服务先写景点，再按提交的顺序重写该景点的 `spot_image`。这样后台“图片”不需要单独的页面，也不会留下孤儿图。

### 5.3 鉴权规则

`JwtInterceptor` 挂在 `/api/**`。流程是：

1. 预检请求 `OPTIONS` 直接放行。
2. 若有 `Authorization: Bearer`，先解析令牌，再按用户 id 读取数据库。用户不存在、`status` 不是 1，或令牌里的 `ver` 与 `user.token_version` 不一致，都视为未登录。角色和用户名以数据库为准，不采信令牌里的旧角色。令牌损坏时同样视为未登录，而不是抛 500。
3. `/api/admin` 必须是数据库中的 `ADMIN`。令牌仍有效但角色已改为 `USER` 时返回 403，而不是 401。
4. 订单、收藏、`/api/user`、`/api/auth/me`、`/api/notes/mine`，以及游记和评论的非 GET 请求，必须已登录。
5. 请求结束后清理 `ThreadLocal`，避免线程池复用时串号。

令牌有效期 72 小时，签发时写入 `ver`。修改密码会把 `token_version` 加一，旧令牌随后失效。禁用账号不改这个版本号，恢复启用后用新的登录即可；没有 `ver` 的旧令牌不会被接受。密钥长度足以让 jjwt 选择 HS384。密码使用 BCrypt，Python 生成的 `$2b$` 哈希可以被 Java 校验。没有引入 Redis。

## 6 关键实现

### 6.1 统一响应与异常

`R` 只有 `code`、`message`、`data`。`GlobalExceptionHandler` 处理四类情况：业务异常 `BizException`、Bean Validation 的字段错误、JSON 读失败、唯一键或外键冲突，以及其他未预料异常。校验失败时把第一条字段提示直接返回，例如“请输入用户名”，而不是一长串框架英文。

前端拦截器在 `code !== 0` 时弹出消息；401 则清除本地令牌并跳到登录页。组件里 `await api.xxx()` 拿到的已经是 `data`，不必每页判断 `code`。

### 6.2 预约与库存

`OrderService.create` 标了 `@Transactional`。顺序是：

1. 景点必须存在且上架。
2. 票种必须在售，且属于该景点。防止用 A 景区的票种给 B 景区下单。
3. 游玩日期在今天到未来 60 天之间。今天是 `LocalDate.now(ZoneId.of("Asia/Shanghai"))`，不跟 JVM 以外的默认时区走。前台日期控件用 `Asia/Shanghai` 的年月日构造禁用范围，避免浏览器停在 UTC 时把上海的“今天”当成昨天。
4. 在同一事务里先 `SELECT * FROM ticket_type WHERE id = ? FOR UPDATE`，锁住这一行票种，再 `SELECT SUM(quantity) … FOR UPDATE` 锁定读取该票种、该日期、状态不是 `CANCELLED` 的数量。可重复读下，事务开头的普通查询会定下快照；若已售统计仍是普通 `SUM`，后拿到票种行锁的那一笔看不见对方刚提交的订单，两笔各买满库存会一起成功。锁定读读到的是最新已提交数据，因此第二笔会按真实已售拒绝。加上本次数量后不得超过锁定行上的 `daily_stock`。两把锁都保持到事务提交。
5. 写入订单。单价和金额取锁定行上的价格，作为当时的快照。订单号由时间和随机数组成，并有唯一索引。

数量由参数校验限制在 1 到 6。用户取消和管理员改状态都执行 `UPDATE booking_order SET status=? WHERE id=? AND status='PENDING'`，受影响行数为 0 就拒绝。因此只能从待出行改为已完成或已取消，已取消和已完成不能改回待出行。取消不删除行，以便统计和用户自己的历史还在。因为已售查询排除了取消单，库存会自动回来，不需要另做一张库存流水。下单时的票种行锁和已售 `SUM … FOR UPDATE` 保持不变。

演示环境没有支付。提交成功只表示预约记录写好了。

![游客预约门票的时序](diagrams/seq-booking.png)

时序从左到右是游客、预约页、`OrderService` 和 MySQL。预约页先按上海日历禁掉今天之前和 60 天之后的日期，服务端再用同一个时区复核，两边不一致时以服务端为准。通过之后先锁票种行，再用 `SUM … FOR UPDATE` 数这一天的已售，然后插订单。取消把状态改成 `CANCELLED`，下一次余票统计不再把这一行算进去。本机复测时，上海日期 2026-10-23 可以下单，同一台 UTC 机器上的 2026-10-22 被拒绝，返回“游玩日期需在今天起 60 天内”。并发复测把 1 号票种日库存临时改为 6，linwan 与 zhouan 在 2026-11-12 同时各买 6 张，只有订单 `SH202610230310051550` 成功，另一笔返回“当日余票不足，剩余 0 张”；再买 1 张同样被拒绝。测完已把日库存改回 6000，并取消成功的那一笔。脚本是 `scripts/oversell_check.py`。

### 6.3 游记审核与点赞

新游记状态固定为 `PENDING`，即使客户端传了别的状态也不会被采信。公开分页只查 `APPROVED`。详情在未通过时，若当前用户不是作者也不是管理员，返回“不存在或尚未通过审核”，避免用 id 把草稿猜出来。

编辑使用 `LambdaUpdateWrapper` 把 `reject_reason` 设为 `NULL`。如果用普通 `updateById`，MyBatis-Plus 默认会跳过 null，旧的驳回原因会留下来。

点赞先要求游记已通过。`note_like` 有 `(note_id, user_id)` 唯一键。已存在则删除并减少计数，不存在则插入并加一。

曾有一个缺陷：未关联景点的游记在组装展示字段时，景点集合为空就使用了 `Map.of()`。这种 Map 不允许用 null 当键，`get(null)` 会空指针，详情接口 500。现已改为普通 `HashMap`，并在 `spotId` 为空时跳过景点查询。走查时发现该问题，修复后重新验证了投稿。

![游记审核的时序](diagrams/seq-audit.png)

审核时序把作者、服务、管理员和访客分开。投稿写入的状态只可能是 `PENDING`。这段时间公开列表和访客详情都看不到正文，作者自己打开仍能读到待审标记。管理员通过之后访客才能评论和点赞。作者若再编辑，状态回到待审，驳回原因被写成 `NULL`，正文再次对访客隐藏。驳回必须带原因，否则对话框不提交。本轮接口脚本走完了这条链：新游记编号 11，审核后公开接口里的 `status` 为 `APPROVED`。

### 6.4 首页缓存与统计

`HomeService.load` 使用 `@Cacheable("home")`。Caffeine 配置为最多 300 条、写入后 120 秒过期。其他服务不能在同类里调用自己的 `@CacheEvict`（那是自调用，代理不会生效），因此单独提供 `HomeCache.evict()`，在景点、游记、轮播、资讯变更后调用。

统计接口做四件事：

1. 近 14 日订单数和金额。`orderTrend()` 只查一次，同一次结果同时填入订单数和金额。没有订单的日期补 0，折线不会断开。
2. 有效订单最多的 8 个景点，画横向柱状图。
3. 近 14 日新增用户。
4. 各分类的景点数量，画饼图。

SQL 按 `DATE(created_at)` 分组，Java 再把结果铺到连续日期上。种子数据用 `DATE_SUB(TIMESTAMP(CURDATE(), ...), INTERVAL n DAY)` 生成，所以无论哪一天导入，图上都覆盖导入日之前的两周。

### 6.5 起价

景点的 `price_from` 是展示用起价，种子数据和保存票种用同一条规则：取该景点在售票的最低价。故宫成人票 60 元、优惠票 30 元，列表和详情的起价是 30 元。保存票种后服务重算这个字段；票种改到另一个景点时，旧景点和新景点都会重算。已经有订单的票种不能修改所属景点。没有任何在售票时，`price_from` 写成 NULL，列表和详情显示“暂无可预约门票”，不保留旧价，也不显示“免费”。免费景区的最低价为 0，前台显示“免费”，同时仍提供“免票预约”和一项 60 元的体验票，让免费景区也能走通下单。

### 6.6 前端交互

除了组件库本身，页面上还有这些自己编写的行为：

1. 列表筛选会写回地址栏，刷新后条件还在。
2. 详情画廊点击缩略图切换主图，并显示该图的署名。
3. 视频元素始终渲染。没有 `video_url` 时只显示封面和说明；有地址则带控制条播放。
4. 顶栏搜索跳到景点列表。手机上导航默认隐藏，点“菜单”展开。样式类必须写在 `<nav class="nav">` 上，否则媒体查询不会生效。这一点在手机走查时修正过。
5. 个人中心用标签页切换资料、收藏和我的游记。
6. 管理端表格内可以直接改订单状态，游记驳回使用输入框收集原因。
7. 统计页在数据返回并完成布局后再初始化 ECharts，并在窗口尺寸变化时 `resize`，避免画布宽度为 0。
8. 景点、游记、资讯、路线详情和游记编辑都 `watch` 路由参数 `id`。从 `/spots/1` 点到同分类的另一处时，组件不会拆掉再建，监听会清空旧图集和评论再请求新 id。
9. 景点详情在正文下给出最多 3 个同分类景点，封面和名称链到对应详情，用来走上面这条监听。
10. 宽度不超过 640 像素时，顶栏那一行的搜索框隐藏，展开“菜单”后在导航底部出现同一个关键词的搜索框，提交后仍跳到景点列表。
11. 介绍视频监听 `error`。浏览器解不出 `.ogv` 时，播放器换成一句“当前浏览器无法播放此格式”，并保留署名里的原始页面链接。

视觉上使用松绿、朱砂、纸色和宋体标题，而不是组件默认的蓝色后台皮肤。主色通过 CSS 变量覆盖 Element Plus 的 primary。

## 7 界面、素材与许可

### 7.1 素材从哪里来

`docs/media-manifest.json` 描述 24 个景点和 5 张横幅。每个景点有一段中文简介、省、市、分类、三张大图、一张缩略图，以及可选的视频对象。`scripts/build_seed.py` 读取这份清单，生成 `sql/data.sql`。图片文件放在 `frontend/public/media/images/`，路径与清单里的 `file` 字段对应，前面加上 `/media/`。

简介文字由媒体包编写，可自由用于本课程网站。票价、开放时间和经纬度是项目根据公开信息填写的演示值，不代表景区实时公示。

封面用缩略图（大约 400 像素宽），画廊用宽度不超过 1280 像素的 WebP，横幅最宽 1920 并裁成约 16:7。这样列表不会为了九张卡片去下载九张大图。

### 7.2 许可

全部图片来自 Wikimedia Commons，只收录 CC0、CC BY、CC BY-SA 或公有领域作品。使用时遵守这些要求：

1. CC BY、CC BY-SA 必须署名作者、写出协议，并给出原始页面。详情页图注包含这三项，其中原始页面是可点击的链接。全站汇总在《素材署名》。
2. CC BY-SA 的改编（缩放、转 WebP、轻微平滑、横幅裁切）仍以相同方式共享。本仓库不额外对图片主张专有权利。
3. CC0 和公有领域没有强制署名，页面上仍然写了作者，以示来源。
4. 视频没有下载进仓库。原来有片源的景点仍记录 Commons 上的文件地址；九寨沟、桂林漓江、泰山、苏州拙政园、乐山大佛、张掖丹霞、厦门鼓浪屿、三亚亚龙湾、重庆洪崖洞改为 Archive.org 直链，地址中的 `#t=` 表示从第几秒开始播放。这些 Archive.org 文件不是 CC 授权，版权归原作者，只用于课程展示，国内部分网络可能较慢。峨眉山、曲阜三孔、平遥古城目前没有 `video_url`，详情页不渲染播放器，只提示浏览图集。播放时在视频下方显示作者、协议和原始页面。故宫和黄山的文件是 Ogg（`.ogv`）。能解码的浏览器直接播放；不能解码时详情页显示“当前浏览器无法播放此格式”，并链到原始页面。黄果树与张家界共用一条中新网短讯，片头是张家界、后半段才是黄果树。这个说明写在该景点的 `video_credit` 和详情正文里，署名仍保留中国新闻网、CC BY 3.0 和文件页链接。
5. 页脚有“素材署名”链接，管理后台编辑景点时也可以改 `video_url` 和每张图的 `credit`。换图不需要改 Java 或 Vue 的业务逻辑。

具体到每一张图的作者和文件页，以 `docs/ATTRIBUTION.md` 为准。例如故宫第一张图的作者是 xiquinhosilva，协议为 CC BY 2.0；兵马俑中有 Gary Todd 的 CC0 作品；横幅分别对应八达岭、张家界、九寨沟、张掖丹霞和外滩。

## 8 测试

### 8.1 环境

本机验收时使用 JDK 21 运行按 Java 17 字节码编译的后端，Node.js 22 运行 Vite，MySQL 8.0 导入 `schema.sql` 与 `data.sql`。导入时会话时区设为 `+08:00`。后端端口 8088，前台端口 43123。把本章所在的这份报告按 A4、页边距 2.54 厘米、小四号、1.5 倍行距导出，插图拉满版心宽度。同目录 `网站设计报告.pdf` 按该版式导出，本版为 59 页。汉字用全角字体计量，和宋体小四的占位一致。

Docker Compose 文件已经写好，包含 MySQL 初始化脚本、后端和 Nginx 前端。当前这台环境没有 Docker 守护进程，因此没有在这里执行 `docker compose up`。文件本身按常规 Compose 写法，可在装有 Docker 的机器上构建。

### 8.2 接口主流程

脚本 `scripts/e2e_api.py` 依次执行：按“西湖”检索、注册新用户、为故宫下两张票、在我的订单中看到该单、取消、投稿游记、管理员审核通过、再次读取公开游记、读取统计。游玩日期取上海时区的今天再加 7 天，不写死某一天。2026-10-23 这一轮的结果是：订单 `SH202610230246269151`，金额 60.00，状态从 `PENDING` 变为 `CANCELLED`；游记编号 11，公开接口中的 `status` 为 `APPROVED`；统计为用户 17、订单 62、待审游记 2、趋势日期 14 个。断言失败会直接退出。

### 8.5 已知限制

1. 没有支付，也没有短信或实名。
2. 票价和库存是演示值。敦煌莫高窟和布达拉宫的日库存故意设得更紧，只为演示“余票不足”。
3. `.ogv` 在部分浏览器里不能解码。播放失败时页面提示“当前浏览器无法播放此格式”，并给出原始页面。换成 WebM 地址即可，不必改播放器。
4. 首页缓存最长 120 秒。审核刚通过时，若正好命中缓存，首页可能晚一点才出现新游记；管理端的写操作会主动清缓存。
5. 上交目录名使用「学号+班级」，学号由提交人自己填写，仓库不编造。排除项和命令写在 `docs/打包说明.md`。
6. 照片包解压后约 9.4 MB，加上源码和压缩过的截图，整体略高于 10 MB，这是照片本身的体积，不是未压缩的原图。

## 10 总结

山河纪把文旅门户里最常被使用的路径做成了可以互相跳转的前后端系统：浏览、筛选、看图和视频、读路线、写游记、预约和取消、审核和统计。数据表按实体拆开，订单保留价格快照，点赞和收藏有唯一约束，图片和视频只存在数据字段里。

媒体包接入之后，24 个景点的封面、画廊和 5 张横幅都改为本地 WebP。介绍视频只存外链：原有 Wikimedia 地址保留，另有 9 个景点使用 Archive.org，峨眉山、曲阜三孔、平遥古城仍为空。署名放在图注、视频说明和《素材署名》三处。图片满足 CC BY / CC BY-SA 的基本要求；Archive.org 视频不是 CC 授权，只用于课程展示。视频文件不进仓库，避免把上百兆的原始图片或视频放进课程压缩包。

预约日期已经按上海时区在前后端同时判断。下单时先锁票种行，再对当天已售做 `SUM … FOR UPDATE`，两笔同时买满库存只会成功一笔。登录和注册的背景改为媒体包里的横幅照片。上交时把目录改成自己的学号加班级，并按 `docs/打包说明.md` 排除 `node_modules`、`dist` 和 `target`。这些是交付时的整理，不是未完成的业务功能。

3. 待审游记不对访客返回正文。
4. 订单取消核对用户 id。
5. 注册用户名有格式校验，减少一阵奇怪字符进库。
6. 全局异常不向前端暴露 SQL。
7. 演示令牌密钥写在 `application.yml`，只适合课程。若部署到公网，应改为环境变量，并缩短有效期。
8. 评论和游记按纯文本保存和展示，不把用户输入当 HTML 插入，降低跨站脚本的风险。
